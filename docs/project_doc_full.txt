1. نظرة عامة
الفكرة: برنامج ويندوز يعمل بالكامل على جهاز المحل بدون إنترنت، ويدير البيع بالباركود، والمخزون وتواريخ الصلاحية، والمشتريات والموردين، والخزنة، والتقارير.
المشاكل الشائعة التي نستهدفها (سيتم التأكد منها في جلسة العميل):
الجرد بالورقة أو الإكسل، وفروق بين المخزون الفعلي والمسجل
اكتشاف المنتجات منتهية الصلاحية بعد فوات الأوان
بطء البيع وأخطاء الكاشير في الأسعار
صعوبة معرفة الربح الحقيقي لكل منتج وكل يوم
ضياع البيانات عند تعطل الجهاز أو انقطاع الكهرباء
الأهداف:
بيع سريع بالباركود، والفاتورة العادية في ثوانٍ
مخزون دقيق، ولكل تغيير في الكمية سبب مسجل ومستخدم مسؤول
تنبيه مبكر للصلاحية القريبة والنواقص والراكد
ثبات عالٍ: لا تضيع بيانات حتى لو انقطعت الكهرباء في منتصف عملية بيع
سهولة: كاشير جديد يتعلم الشاشة في ساعة واحدة
أن يكون المنتج قابلًا للتخصيص بحيث يصلح لمحلات أخرى لاحقًا
أولويات التصميم (بالترتيب): صحة البيانات، ثم السرعة، ثم البساطة، ثم الشكل.
افتراضات تحتاج تأكيدًا من العميل:
جهاز واحد في المحل (كاشير واحد)
ويندوز 10 أو 11
سكانر باركود USB وطابعة إيصالات حرارية 80mm
المحل لا يحتاج الفاتورة الإلكترونية حاليًا (يُراجع مع المحاسب)

4. الوحدات بالتفصيل
4.1 المنتجات والباركود
المنتج: الاسم بالعربي والإنجليزي، الماركة، القسم، الوحدة، صورة اختيارية، حد أدنى للمخزون، الحالة (نشط أو مؤرشف)
الـ Variant: درجة اللون أو الحجم أو العبوة، ولكل variant سعر بيع وباركود وSKU خاص به. (روج بثلاث درجات = منتج واحد وثلاثة variants)
باركودات متعددة للـ variant الواحد: باركود المصنع وباركود داخلي إن لزم
توليد باركود داخلي بصيغة EAN-13 بأرقام فقط مع رقم تحقق (check digit)، وبادئة مخصصة للاستخدام الداخلي حتى لا يتعارض مع باركودات المصانع
طباعة ملصقات بحجم قابل للضبط، واختيار منتجات متعددة وعدد النسخ
استيراد من Excel أو CSV: معاينة، وتقرير أخطاء (باركود مكرر، سعر ناقص، قسم غير معروف) قبل التأكيد
تحديث بالجملة للأسعار والأقسام والماركات
بحث بالاسم أو الماركة أو الباركود أو جزء منه
أرشفة بدل الحذف، فلا يختفي منتج ظهر في فواتير سابقة
منع التكرار: الباركود فريد على مستوى قاعدة البيانات
4.2 البيع (نقطة البيع POS)
حقل الباركود دائمًا في حالة تركيز، ويعود إليه التركيز تلقائيًا بعد أي عملية
مسح الباركود يضيف الصنف، ومسحه مرة أخرى يزيد الكمية واحدًا
باركود غير موجود: صوت تنبيه ونافذة "إضافة منتج جديد بهذا الباركود"
بحث يدوي سريع بالاسم (F2) للمنتجات التي لا يُقرأ باركودها
تعديل الكمية، حذف سطر، خصم على السطر أو على الفاتورة (نسبة أو مبلغ) ضمن حدود الصلاحية
طرق الدفع: نقدي، بطاقة، محفظة إلكترونية، آجل، ودفع مجزأ على أكثر من طريقة
تعليق الفاتورة (Hold) واسترجاعها لخدمة عميلين بالتوازي
FEFO تلقائي: يُخصم من الدفعة الأقرب انتهاءً أولًا
منع بيع الدفعات منتهية الصلاحية، وتحذير عند الاقتراب منها
سلوك المخزون الصفر حسب الإعدادات (منع أو تحذير)
الفاتورة نهائية بعد الحفظ: لا تُعدل ولا تُحذف، والتصحيح يتم بمرتجع أو إلغاء بسبب مسجل ومستخدم مسؤول
ترقيم تسلسلي بلا فجوات
إيصال 80mm، وإعادة الطباعة، وخيار A4
تسجيل سعر البيع والتكلفة واسم الصنف داخل سطر الفاتورة وقت البيع (snapshot) حتى لا تتغير الفواتير القديمة بتغير الأسعار

4.3 المخزون
الدفعات (Batches): كل استلام ينشئ دفعة لها رقم وتاريخ صلاحية وتكلفة وكمية. وبذلك تكون التكلفة والربح دقيقين لكل بيعة
أنواع الحركات: استلام شراء، بيع، مرتجع بيع، مرتجع شراء، تسوية جرد بالزيادة أو النقص، هالك، منتهي الصلاحية، تستر وعينات
القاعدة الذهبية: لا يتغير رصيد المخزون إلا بحركة مسجلة، ولا يوجد تعديل مباشر على الرقم
الجرد: إنشاء دورة جرد (كل المحل أو قسم أو ماركة)، ثم مسح وعد المنتجات، ثم مقارنة بالنظام، ثم تقرير فروقات، ثم اعتماد التسوية بصلاحية مدير
التنبيهات: صلاحية قريبة (30 و60 و90 يومًا، قابلة للتعديل)، نواقص تحت الحد الأدنى، راكد لم يُبع منذ فترة
قيمة المخزون بالتكلفة وبسعر البيع، وبالقسم والماركة
4.4 المشتريات والموردين
بيانات المورد ورصيده وكشف حسابه
فاتورة شراء بالمسح: كمية، تكلفة، رقم الدفعة، تاريخ الصلاحية، وسعر بيع مقترح مع خيار تحديث سعر البيع
دفع نقدي أو آجل، وتسجيل دفعات سداد للمورد
مرتجع شراء
تاريخ تكلفة كل صنف ومقارنة بين الموردين
4.5 المرتجعات والاستبدال
المرتجع مرتبط بالفاتورة الأصلية، ولا تتجاوز الكمية المرتجعة الكمية المباعة
حالة المنتج المرتجع: صالح فيعود للمخزون، أو تالف فيُسجل هالكًا
رد نقدي أو رصيد للعميل
الاستبدال = مرتجع + بيع جديد في عملية واحدة
سياسة قابلة للضبط: مستحضرات التجميل المفتوحة قد لا تُرجع لأسباب صحية، لذا مدة الإرجاع وشروطه تُحدد من الإعدادات
4.6 العملاء والآجل

4.7 الخزنة والورديات والمصروفات

6. تصميم قاعدة البيانات
6.1 المبادئ
المبالغ بالقروش كأعداد صحيحة (INTEGER) لتجنب أخطاء الكسور العشرية. مثال: 150.75 جنيه تُخزن 15075.
التواريخ بصيغة ISO وبتوقيت UTC، وتُعرض بتوقيت القاهرة.
كل جدول رئيسي له id رقمي وuuid نصي فريد، تجهيزًا لأي مزامنة مستقبلية.
لا حذف فعلي لأي بيانات مرتبطة بعمليات: أرشفة (is_active) أو إلغاء بسبب مسجل.
سطر الفاتورة يحفظ لقطة (snapshot) من الاسم والسعر والتكلفة وقت البيع.
القيود على مستوى القاعدة نفسها: PRIMARY KEY وFOREIGN KEY وUNIQUE وCHECK وNOT NULL، فلا تدخل بيانات خاطئة حتى لو وُجد خطأ في الكود.
المخزون = مجموع حركات مسجلة. كمية الدفعة تتغير عن طريق trigger عند تسجيل حركة فقط.
6.2 الجداول الرئيسية
6.3 الجداول الحرجة (مخطط مبدئي)
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA synchronous = FULL;
PRAGMA busy_timeout = 5000;

CREATE TABLE product_variants (
  id INTEGER PRIMARY KEY,
  uuid TEXT NOT NULL UNIQUE,
  product_id INTEGER NOT NULL REFERENCES products(id),
  name TEXT,                       -- shade / size
  sku TEXT UNIQUE,
  sale_price INTEGER NOT NULL CHECK (sale_price >= 0),  -- piasters
  min_stock INTEGER NOT NULL DEFAULT 0,
  is_active INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE product_barcodes (
  id INTEGER PRIMARY KEY,
  variant_id INTEGER NOT NULL REFERENCES product_variants(id),
  barcode TEXT NOT NULL UNIQUE,
  is_internal INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE batches (
  id INTEGER PRIMARY KEY,
  variant_id INTEGER NOT NULL REFERENCES product_variants(id),
  batch_no TEXT,
  expiry_date TEXT,                -- YYYY-MM-DD or NULL
  unit_cost INTEGER NOT NULL CHECK (unit_cost >= 0),
  qty_remaining INTEGER NOT NULL CHECK (qty_remaining >= 0),
  received_at TEXT NOT NULL
);

CREATE TABLE stock_movements (
  id INTEGER PRIMARY KEY,
  batch_id INTEGER NOT NULL REFERENCES batches(id),
  type TEXT NOT NULL CHECK (type IN
    ('purchase','sale','sale_return','purchase_return',
     'adjust_in','adjust_out','expired','tester')),
  qty INTEGER NOT NULL CHECK (qty <> 0),  -- + in, - out
  ref_type TEXT, ref_id INTEGER,
  user_id INTEGER NOT NULL REFERENCES users(id),
  note TEXT,
  created_at TEXT NOT NULL
);

CREATE TRIGGER trg_movement_apply AFTER INSERT ON stock_movements
BEGIN
  UPDATE batches SET qty_remaining = qty_remaining + NEW.qty
  WHERE id = NEW.batch_id;          -- CHECK fails => whole sale rolls back
END;

CREATE TRIGGER trg_movement_no_update BEFORE UPDATE ON stock_movements
BEGIN SELECT RAISE(ABORT, 'stock_movements is append-only'); END;

CREATE TRIGGER trg_movement_no_delete BEFORE DELETE ON stock_movements
BEGIN SELECT RAISE(ABORT, 'stock_movements is append-only'); END;
الفواتير: جدول sales (رقم تسلسلي، المستخدم، الوردية، العميل، الإجمالي، الخصم، الحالة) وsale_items (variant_id، batch_id، الكمية، سعر البيع، التكلفة، الاسم وقت البيع) وsale_payments (طريقة الدفع والمبلغ). كل حركة نقدية تُسجل في cash_movements مرتبطة بالوردية.
6.4 قواعد النزاهة
لا يمكن أن تقل كمية الدفعة عن صفر، وأي بيع زائد يفشل ويُلغى بالكامل.
حركات المخزون للإضافة فقط: لا تعديل ولا حذف. التصحيح بحركة معاكسة.
الفاتورة المكتملة لا تُعدل (trigger)، والتصحيح بمرتجع أو إلغاء بسبب.
رقم الفاتورة يُؤخذ من جدول counters داخل نفس الـ transaction، فلا فجوات ولا تكرار.
مجموع المدفوعات يساوي صافي الفاتورة، ويُتحقق منه في الخدمة وفي الاختبارات.
لا حذف لمنتج أو مورد أو عميل له حركات.
7. التقنية والأدوات المقترحة
ملاحظات مهمة:
تحقق من نسخة ويندوز في جهاز المحل أولًا. النسخ الحديثة من Electron لا تعمل على ويندوز 7 و8، فلو الجهاز قديم نحتاج نسخة Electron أقدم أو تغيير الجهاز.
better-sqlite3 مكتبة native تحتاج إعادة بناء مع نسخة Electron المستخدمة، وelectron-builder يتولى ذلك، لكن نختبر الـ installer على جهاز نظيف مبكرًا.
لا خدمات خارجية ولا CDN ولا اتصال بالإنترنت أثناء التشغيل: الخطوط والأيقونات كلها داخل التطبيق.
بدائل أُخذت في الاعتبار: Tauri أخف حجمًا لكنه يحتاج Rust، وتطبيق Python/Qt لا يتناسب مع خبرة الفريق في الويب. لذلك Electron هو الخيار الأنسب هنا.
8. المعمارية
8.1 العمليات الثلاث
Main process: قاعدة البيانات، المنطق التجاري، الطباعة، النسخ الاحتياطي، الملفات.
Preload: يعرض واجهة ضيقة وآمنة (contextBridge) للواجهة بدون إعطائها صلاحيات النظام.
Renderer: واجهة React فقط. لا وصول مباشر للقاعدة، وكل طلب يمر عبر IPC ويُتحقق منه بـ Zod. إعدادات الأمان: contextIsolation: true وnodeIntegration: false.
8.2 الطبقات
الواجهة ← IPC ← الخدمات (Use Cases) ← المستودعات (Repositories) ← SQLite.
المنطق التجاري (حساب الخصم، اختيار الدفعات FEFO، الضريبة، الأرصدة) دوال TypeScript نقية قابلة للاختبار بدون واجهة، ويمكن لاحقًا نقلها لخادم إن احتجنا مزامنة سحابية.

8.4 مسار عملية البيع
الواجهة ترسل الأصناف والمدفوعات والعميل ورقم الوردية عبر IPC.
الـ main يتحقق من المدخلات بـ Zod.
يبدأ transaction من نوع BEGIN IMMEDIATE.
يختار الدفعات بنظام FEFO ويحسب الأسعار والخصومات.
ينشئ الفاتورة وسطورها والمدفوعات، ويسجل حركات المخزون (والـ trigger يحدّث الدفعات)، وحركة الخزنة، ويزيد العداد، ويكتب سجل العمليات.
COMMIT. وإن حدث أي خطأ: ROLLBACK وتعود رسالة واضحة للكاشير، ولا يبقى أثر.
بعد النجاح فقط تبدأ الطباعة. فشل الطابعة لا يلغي البيع، ويظهر زر "إعادة الطباعة".
9. استراتيجية "صفر أخطاء"
لا يوجد برنامج بلا أخطاء بشكل مطلق. الهدف الواقعي: منع الأخطاء قبل حدوثها قدر الإمكان، وجعل الباقي لا يفسد البيانات، وتمكين الاسترجاع السريع.
10. خطة التنفيذ على مراحل
المدد تقديرية وتتوقف على حجم الفريق وعدد ساعات العمل. الفكرة أن يبدأ صاحب المحل في رؤية السيستم وتجربته مبكرًا، فنأخذ ملاحظات حقيقية بدل الانتظار حتى نهاية المشروع.
نقاط قرار مع العميل: بعد المرحلة 2 (يرى شاشة البيع ويقيّمها)، وبعد المرحلة 3 (يتأكد من منطق المخزون والصلاحية)، وقبل التسليم النهائي.
11. المخرجات النهائية
ملف التثبيت setup.exe
دليل مستخدم عربي مختصر بالصور، وفيديو قصير لتدريب الكاشير
دليل المطور (README): التشغيل والبناء والـ migrations
بيانات تجريبية (seed) لتجربة النظام
قائمة اختبار التسليم (checklist)
خطة الدعم بعد التسليم: قناة التواصل، وقت الاستجابة، وطريقة إصدار الإصلاحات وترقية النسخة بدون فقدان بيانات
دليل الاسترجاع الطارئ: ماذا نفعل إذا تعطل الجهاز، وكيف نسترجع من النسخة الاحتياطية
12. الأجهزة الموصى بها
كمبيوتر بويندوز 10 أو 11، ذاكرة 8GB أو أكثر، وقرص SSD

سكانر باركود USB (يفضل أن يدعم 1D و2D، وأن يرسل Enter بعد كل قراءة)

درج نقدية يُفتح من الطابعة (اختياري)
طابعة ملصقات حرارية (اختيارية، تكفي الطابعة العادية في البداية)
فلاشة أو هارد خارجي للنسخ الاحتياطي

14. أسئلة لجلسة العميل (المرحلة 0)
كم جهاز وكم كاشير في المحل؟ وهل يوجد أكثر من فرع؟
ما نسخة ويندوز على الجهاز؟ وما مواصفاته؟
كيف يدير البيع والجرد الآن؟ (دفتر، إكسل، برنامج) وما الذي يزعجه فيه؟
كم عدد المنتجات تقريبًا؟ وهل لدى أغلبها باركود؟ وهل لديه ملف إكسل بها؟
هل يبيع بالأجل؟ ولمن؟ وهل هناك حد ائتمان؟
هل يتعامل بالخصومات والعروض؟ وما أنواعها؟ (نسبة، مبلغ، كومبو، عروض موسمية)
هل يتعامل مع منتجات تحتاج متابعة صلاحية؟ وما المدة المناسبة للتنبيه؟
كيف يتعامل مع المرتجعات والاستبدال؟ وما سياسته للمنتجات المفتوحة؟
ما شكل الفاتورة أو الإيصال الذي يريده؟ وهل يريد اللوجو؟
هل المحل مسجل ضريبيًا ويحتاج فاتورة إلكترونية؟ (يسأل المحاسب)
ما التقارير التي يريد رؤيتها يوميًا؟
من سيستخدم النظام؟ ومن يرى الأرباح والتكلفة؟
ما السكانر والطابعة الموجودان؟ وهل لديه درج نقدية؟
هل يستخدم موردين بحسابات آجلة؟ وكيف يتابعها؟
هل سبق أن فقد بيانات؟ وكيف حدث؟
ما الميزة التي لو وجدت في السيستم لقال "هذا هو ما أحتاجه"؟
15. تطويرات لاحقة (بعد الإصدار الأول)
مزامنة سحابية ونسخ احتياطي أونلاين
تعدد الفروع والأجهزة
نقاط الولاء وبطاقات العملاء
تطبيق موبايل لمتابعة المبيعات والمخزون، وجرد بكاميرا الهاتف
إرسال الفاتورة عبر واتساب
ربط الفاتورة الإلكترونية بمصلحة الضرائب
تحويل المنتج إلى نسخة قابلة للبيع لمحلات أخرى (white-label) بإعدادات وأسعار وتراخيص
توصيات إعادة الطلب حسب سرعة البيع
16. الخطوات التالية
تحديد موعد جلسة المرحلة 0 مع صاحب المحل بقائمة الأسئلة أعلاه.
فحص الجهاز والطابعة والسكانر في المحل.
تحويل إجاباته إلى وثيقة متطلبات نهائية وتعديل هذه الوثيقة بناءً عليها.
تصميم الشاشات الأساسية (شاشة البيع أولًا) والاتفاق على الهوية.
اعتماد الـ schema النهائي وبدء المرحلة 1.
